## 原因与修正

本机历史实测中，1470×956 下刘海辅助区间隙为179×32 pt，1280×832 下为156×28 pt；原展开壳480×200、窗口520×240、Host画布及字体/两翼一直用固定point。由此展开壳相对刘海的宽度比例变化约14.7%。两档backingScale均2，不能用backing像素倍率修复布局。

[IslandDisplayLayout](../../DynamicIsland/IslandDisplayLayout.swift)以有效辅助区高度÷32生成统一layout scale。32 pt是当前默认显示的设计参考；菜单栏可见区域高度不参与倍率。无有效刘海时保持1倍，再按屏幕窗口预算等比fit。未承诺极小虚构显示尺寸或任意设备组合。

[IslandView](../../DynamicIsland/IslandView.swift)保持Host标准设计画布，只执行一次统一变换，字体、图标、圆角、阴影、控件与壳体同步。实际刘海间隙反归一后交给Renderer，最终仍精确保留真实中心避让宽度。窗口、紧凑/展开悬停区消费同一份metrics；分数尺寸保留精确顶边和中心，避免单独取整原点产生偏移。环境变化沿用ScreenManager事件通知，不新增轮询。

八字符原生计时`02:00:00`的像素回归发现原126 pt两翼增量间距不足，调整为150 pt；宽时间框、边缘和中心避让保留各自预算。诊断报告新增四位小数`layout_scale`，便于实测区分布局倍率与backing scale。SDK、Activity/Node协议和权限语义未改。
