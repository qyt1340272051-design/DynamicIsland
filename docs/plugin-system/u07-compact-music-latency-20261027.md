# U07 — 收起态音乐更新延迟（2026-10-27）

用户反馈音乐信息最慢约 9 秒，进一步说明展开时较及时，收起时偶有十多秒不变，移入鼠标展开后才更新。目标为 App 0.6.1 / build13，重点覆盖非激活、收起态。

## 探测与边界

- 当前设备直接执行相同只读 helper：6 次查询为 76–103 ms，中位数 85 ms；另一独立 8 次为 81.5–101.7 ms，中位数 95.3 ms。没有发送控制命令。
- 已运行 build12 的 12 秒后台子进程采样共看到 7 次读取，相邻启动约 1.62–1.74 秒。本次采样未捕获用户的十多秒卡住现场。
- 真实非激活、可见面板的同一 `IslandView` 自动刷新回归不靠手动刷新或悬停，可以更新曲目及迟到 / 替换封面；一次来源变更到模型应用为 1199 ms。因此不把普通固定资源 ID 单独当作整个现象的唯一原因。
- 活动监视器本次显示 App Nap 为“否”；未据此排除其他时刻的后台合并，但没有设置全局禁用 App Nap，也没有永久禁止系统睡眠。
- 查询本身包含封面等待，旧循环在请求结束后额外睡眠 1.5 秒。单次 Host deadline 6 秒再加下一轮等待会放大异常恢复时间。并行手动 / 展开 / 定时刷新还存在旧响应覆盖新响应的确定性竞态。

## 修正

- 可见岛使用限定容差的 Dispatch 定时器，周期保持 1.5 秒；收起时仍执行，隐藏时取消，重新显示立即开始。每次最多一个轮询，慢请求跳过重复 tick，恢复后不补发一串旧任务。
- 用请求序号隔离过期成功 / 失败；已有来源 generation、seek generation 与权限校验保留，播放控制开始时也使更早的读取过期。
- 普通元数据读取 deadline 从 6 秒缩至 2 秒；播放控制与 seek 保留 6 秒。显式测试 / 诊断 timeout 覆盖保持有效。
- Host 封面内容变化带入资源版本，使纯 Activity 订阅者也能观察并重绘仅有封面变化的快照；不依赖父界面碰巧同时观察音乐模型。旧资源版本不会被解析成新内容，Activity 实例和控制动作保持稳定。
- 增加调试级时序日志，仅含请求序号、紧凑状态、耗时及元数据 / 封面变化布尔值，不记录歌名、歌手、封面字节或账号信息。

特定计时器的严格容差仍属于系统尽力保证，不是硬实时承诺；参见 Apple SDK `dispatch/source.h` 的 `DISPATCH_TIMER_STRICT` 说明及 [Apple 节能与 QoS 指南](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html)。本轮没有将循环加密到每秒数次：0.75 秒目标节奏的只读小样本已消耗约 12.86% 单核子进程 CPU，故不采用该配置。

## 验证

旧代码下，受控旧成功、旧失败和查询后额外等待的三个回归均失败。仅订阅 ActivityManager 的封面资源回归也确认旧快照没有更新、画面仍为旧色。非激活面板的整页原生像素测试、自动轮询、暂停 / 恢复、迟到 / 替换封面作为单独回归保留。

最终构建、完整测试与真实缩小态观察记录见[证据目录](evidence/u07-compact-music-latency-20261027/README.md)。网易云 helper 字节与 SHA-256 保持原值；本轮不修改插件权限、来源或客户端播放，不将当前采样代替原始偶发现场的唯一根因证明。
